# prisma-orm — Prisma checklist (NestJS + PostgreSQL)

**Principle:** the schema and migrations are the database contract, and Prisma is an infrastructure detail. Every decision (version, `onDelete`, retention, invariants Prisma cannot express) comes from the docs of the installed version and is recorded in the project, never from the agent's memory.

## Failure-mode diagnosis

The agent writes schema, migrations and repositories "from memory" and fails in predictable ways:
- mixes conventions (names, `@map`, ids) and reads the docs of another version (the unversioned docs now serve Prisma 8 content, whose CLI does not read `schema.prisma`);
- forgets `prisma format`/`validate` in the hook and CI, and does not decide `onDelete` or retention: it accepts the default without knowing what it is;
- treats `@updatedAt` and raw SQL as equivalent to the client (`@updatedAt` is client-side, not database-side), and lets Prisma types/errors leak into domain and application;
- edits an already-applied migration, or generates a migration and applies it without reading the SQL;
- forgets that Prisma 6 cannot express CHECK, expression indexes, triggers and (without the preview) partial indexes, and drops the invariant instead of recording where it now lives.

Labels: no label = prescription or fact from the official docs; `[community]` = third-party convention/opinion; `[not verified in docs]` = no source read.
Source prefixes: `P6` = prisma.io/docs/orm/v6/ ; `P7` = prisma.io/docs/orm/v7/ ; `PG` = postgresql.org/docs/current/ (v18) ; `NE` = docs.nestjs.com/. Full list in section 18.

## 1. Before touching anything

```bash
grep -E '"(prisma|@prisma/[a-z-]+|@nestjs/core|@nestjs/config)"' package.json   # declared versions
npx prisma -v                                   # effective CLI and client version
psql "$DATABASE_URL" -c 'select version()'      # or: docker compose config | grep -i image
ls prisma/ prisma.config.ts 2>/dev/null; ls prisma/migrations | tail -5
npx prisma migrate status                       # history vs database (exits 1 if diverged)
grep -rEil 'prisma|migration|onDelete|retention' docs/ .specs/ 2>/dev/null | head   # ADRs / constitution
```

- [ ] The CLI version was read and the docs consulted are for that version (`/docs/orm/v6/` or `/v7/`). Without a prefix, the docs are Prisma 8's (RC). (source: orm/release-status; P6/P7)
- [ ] `prisma` and `@prisma/client` are pinned to the same major in `package.json`; `npm install prisma` without a version installs CLI 8, which does not read `schema.prisma`. (source: prisma.io/docs/orm/release-status, accessed 2026-10-14)
- [ ] The project's recorded decisions (constitution, ADRs, decision log) were read. If the project deliberately diverges from this checklist (e.g. app-generated `uuid()`, no physical FK), respect it and do not "fix" it; with no record, apply the checklist and propose recording it.

## 2. Schema, names, types, enums

- [ ] Models are singular PascalCase, fields camelCase; existing or snake_case tables/columns go through `@@map`/`@map`, with one convention across the whole schema. (source: P6 prisma-schema/data-model/models, v6)
- [ ] Every type where precision matters has an explicit `@db.*` (`@db.VarChar(n)`, `@db.Decimal(p,s)`, `@db.Uuid`): without `@db.*` Prisma uses the connector default. (source: P6 models, "Native types mapping")
- [ ] `DateTime` has a time zone decision: the Postgres default is `timestamp(3)` (no time zone); use `@db.Timestamptz(3)` when the instant matters. (source: P6 reference/prisma-schema-reference, PostgreSQL table; the Timestamptz recommendation is `[community]`)
- [ ] Money is `Decimal` with `@db.Decimal(p,s)`, never `Float`. `[community]`
- [ ] The id strategy is decided and uniform: `uuid()` is generated by Prisma Client (it does not show in the database schema; for a database default use `@default(dbgenerated(...))`); `autoincrement()` is serial on Postgres. (source: P6 models, "Defining a default value")
- [ ] `uuid(7)`/`uuid(4)`/`cuid(2)` are used only if the installed version lists them for `@default`. `@default(uuid(7))` is accepted by Prisma 6.19.3 (`prisma validate`, verified on 2026-10-15); like `uuid()`, it is generated on the client: the column stays `uuid`, `migrate diff` comes out empty (prove it with `--from-schema-datamodel <old> --to-schema-datamodel <new> --script`) and there is no data migration; old v4 and new v7 ids coexist. Postgres 16 has no `uuidv7()` (it arrives in 18) and Node 25 has no `crypto.randomUUIDv7`: an id generated in the app uses the `uuid` package (`v7()`), and in a CJS project it ships CommonJS only up to 11.x. `ParseUUIDPipe` (no version) and `z.uuid()` accept v7; check that nothing in the project requires v4.
- [ ] `@default(now())` is a database default on relational databases; `@updatedAt` is not. (source: P6 models)
- [ ] Enums: `@@map` names the native Postgres enum and `@map` names each value; confirm the generated SQL in the migration. On Prisma 7, `@map` on enum values carries a known-bug warning in the reference page while the upgrade guide says the opposite (values = schema names): test before using `@map` on an enum value. (source: P6 prisma-schema-reference; upgrading-to-prisma-7 guide)
- [ ] Every `Unsupported(...)` field is recorded: it disappears from the client, and if required it removes `create`/`update` for the model. (source: P6 models, "Unsupported")
- [ ] No `db push` outside throwaway prototypes: it generates no migration. (source: P6 reference/prisma-cli-reference)

## 3. Relations and `onDelete`

- [ ] Every relation declares `onDelete` and `onUpdate` explicitly, even when equal to the default. Real defaults: optional relation `onDelete: SetNull`; required `onDelete: Restrict`; `onUpdate: Cascade` on both. It is not Cascade nor NoAction. (source: P6 .../relations/referential-actions, v6 and v7 identical)
- [ ] `SetNull` only on an optional FK: on Postgres the schema compiles with a required FK and fails at runtime. (source: P6 referential-actions)
- [ ] Every `Cascade` has a justification (the child is part of the aggregate, not an independent object); independent objects use `Restrict`/`NoAction`. Difference: `NoAction` can be deferred to the end of the transaction, `Restrict` cannot. (source: PG ddl-constraints, v18)
- [ ] The retention/deletion policy for personal data (LGPD) is a recorded decision: truly deleting, anonymizing or soft-deleting decides whether `onDelete` is `Cascade`, `Restrict` or `SetNull`. Prisma has no opinion; legal basis `[not verified in docs]`.
- [ ] `@relation(map: "...")` and indexes with `map` follow a naming pattern, for readable migrations. `[community]`

## 4. Indexes

- [ ] Every FK column has an `@@index` in the schema, unless a decision says otherwise. Postgres does not create an index on the referencing side (only on the referenced one); without it, `DELETE`/`UPDATE` on the parent scans the child. (source: PG ddl-constraints v18; `[community]` cybertec-postgresql.com, "Foreign Key Indexing and Performance", Laurenz Albe, 2018, not read in full) Prisma's index and relation docs do not mention the subject.
- [ ] `@@unique` covers the uniqueness invariant in the database; checking "does it exist?" before inserting is not enough (race): handle P2002. (source: P6 reference/error-reference)
- [ ] Partial indexes, expression indexes, `CONCURRENTLY` and CHECK do not come out of the schema on Prisma 6: they go in migration SQL (sections 6 and 15). (source: P6 prisma-schema-reference, `@@index`; P7 reference/database-features)
- [ ] An index on a large production table uses `CREATE INDEX CONCURRENTLY`, which cannot run in a transaction; check that the migration runner does not wrap the file in a transaction and record the exception. (source: PG sql-createindex v18; Prisma 6 runner behavior with CONCURRENTLY `[not verified in docs]`)

## 5. `@updatedAt` and raw SQL

- [ ] `@updatedAt` is applied by Prisma Client, not by the database; an `update` with empty `data` does not change it. Any write outside the client (raw SQL, another service, `psql`) does not update the column. (source: P6 prisma-schema-reference, "@updatedAt")
- [ ] Every `UPDATE`/`INSERT` in `$executeRaw` sets `updated_at = now()` and generates client-side ids/defaults by hand (`uuid()` does not exist in the database); the docs do not state "raw does not fire `@updatedAt`" (`[not verified in docs]`, inference from the ORM-level design).
- [ ] Raw SQL only via `$queryRaw`/`$executeRaw` as a template tag; `$queryRawUnsafe`/`$executeRawUnsafe` only with `$1` placeholders, never concatenation; a dynamic table/column name comes from a fixed allowlist. `Prisma.raw` with user input is injection. (source: P6 prisma-client/using-raw-sql/raw-queries)
- [ ] Raw results are typed and converted by hand: the engine does not normalize types (`bigint`, `Decimal`, boolean) as the client methods do, and each call runs a single statement. (source: P6 raw-queries)

## 6. Migrations

- [ ] Flow: edit the schema, `npx prisma migrate dev --create-only --name <verb_object>`, **read `migration.sql`**, adjust it, `npx prisma migrate dev`. (source: P6 prisma-migrate/workflows/customizing-migrations)
- [ ] Production, staging and CI apply only `npx prisma migrate deploy`: no reset, no shadow DB, no drift detection; it runs in a pipeline, not by hand. `migrate dev` and `migrate reset` only in dev. (source: P6 workflows/development-and-production)
- [ ] No migration already applied in another environment is edited or deleted: `dev` asks for a reset and `deploy` only warns. The fix is a new migration. Check: `git log --follow prisma/migrations/<dir>/migration.sql` shows a single commit. (source: P6 development-and-production)
- [ ] The generated `migration.sql` is edited only before its first apply, to: preserve data (rename instead of drop/create, backfill), SQL the schema cannot express, `CONCURRENTLY`. Justify with an SQL comment at the top (what and why) and in the commit. (source: P6 customizing-migrations; triggers/extensions appeared as examples in search results, not on the page read)
- [ ] A breaking change (rename, type change, table split) follows expand/migrate/contract across separate releases: add nullable, dual-write, backfill in batches, switch reads, stop writing, remove. (source: P6 customizing-migrations, "expand and contract"; Fowler/Danilo Sato, martinfowler.com/bliki/ParallelChange.html, 2014; prisma.io/dataguide/types/relational/expand-and-contract-pattern `[community]`, high weight)
- [ ] A new constraint on a table with data uses `ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT` (`SHARE UPDATE EXCLUSIVE` lock); a direct `ADD CHECK` takes `ACCESS EXCLUSIVE`. (source: PG sql-altertable v18)
- [ ] Drift/diff check in CI: `npx prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --exit-code` (needs a shadow DB; exits 2 on differences). Triggers, views and anything Prisma does not model do not appear in the diff. (source: P6 reference/prisma-cli-reference; `--from-migrations` requires a shadow DB: prisma-migrate/understanding-prisma-migrate/shadow-database)
- [ ] `npx prisma migrate status` exits 1 on pending, diverged or failed migrations: use it in the pipeline before deploy. A failed migration in production: `migrate resolve --applied|--rolled-back <name>` only after fixing the database by hand. (source: P6 prisma-cli-reference)
- [ ] Existing database without history (baseline): `migrate diff --from-empty --to-schema ... > prisma/migrations/0_init/migration.sql` and `migrate resolve --applied 0_init`. Squash only for history without manual SQL and with everything applied: manual SQL is lost. (source: P6 workflows/baselining and squashing-migrations)
- [ ] `shadowDatabaseUrl` never points to the main database. Migration locks have a fixed 10 s timeout (rerun if it expires). (source: P6 shadow-database; development-and-production)
- [ ] `migrate deploy` (and a `db:migrate:up` that calls it) does **not regenerate Prisma Client**. After applying migrations or pulling a schema change: `npx prisma generate` (or `pnpm install`, if a `postinstall` runs `prisma generate`), build, and restart the process. Symptom of a stale client against an already migrated database (e.g. renamed enum types): `PrismaClientUnknownRequestError` in queries, repeated on every worker cycle, while `readyz` stays ok. Document the step in the project README. (source: observed on 2026-10-15; P6 `prisma generate` builds the client from the schema, not from the database)

## 7. Formatting and validation (hook and CI)

- [ ] `npx prisma format` runs in pre-commit (lint-staged on `**/*.prisma`) and `npx prisma format --check` + `npx prisma validate` run in CI. The exit code of `--check` is not specified in the docs: verify it in the project (`echo $?` with an unformatted file). (source: P6 reference/prisma-cli-reference)
- [ ] `npx prisma generate` runs in `postinstall`/build and in CI; on Prisma 7 `migrate dev` and `db push` no longer run generate or seed. (source: upgrading-to-prisma-7 guide)
- [ ] A schema change without a matching migration fails CI (the `migrate diff` item above).
- [ ] Prisma 6: variables load from `./.env`, then `--schema`, then `prisma/`; if the same name appears in two files, the CLI fails: keep a single `.env`. (source: P6 more/dev-environment/environment-variables)

## 8. Transactions and concurrency

- [ ] `$transaction([...])` (sequential) only for independent operations; logic between queries, read-decide-write or generated ids use `$transaction(async (tx) => ...)`, and all access inside uses `tx`, never the client. (source: P6/P7 prisma-client/queries/transactions)
- [ ] Interactive: `maxWait` 2000 ms and `timeout` 5000 ms are the defaults; keep transactions short, with no network calls or queues inside. Changing the default is a case-by-case decision. (source: P6/P7 transactions)
- [ ] Explicit `isolationLevel` when the invariant depends on it; under `Serializable`, P2034 (conflict/deadlock) requires an application-level retry with an attempt cap. (source: P6/P7 transactions)
- [ ] A row read in order to be changed under concurrency is locked with `SELECT ... FOR UPDATE` (via `$queryRaw` inside the transaction) in a stable id order to avoid deadlock; with `ORDER BY` + lock, PG may return rows out of order at READ COMMITTED. (source: PG sql-select, "The Locking Clause", v18; use via `$queryRaw` in Prisma `[not verified in docs]`)
- [ ] Unit of work: the application defines the transaction boundary per use case; `tx` is propagated through a port (e.g. `UnitOfWork`/context), not as a `Prisma.TransactionClient` parameter in domain signatures. The Nest docs suggest `nestjs-cls` for declarative transactions. (source: NE recipes/prisma; architecture `[community]`)
- [ ] `Promise.all` inside a transaction runs serially (one connection): do not use it to parallelize. (source: P6 transactions)
- [ ] External side effects (email, queue) run after commit, not inside the transaction. `[community]`

## 9. Client in Nest

- [ ] `PrismaService` extends `PrismaClient` and implements `OnModuleInit` (`await this.$connect()`, fails at boot) and `OnModuleDestroy` (`$disconnect()`); `app.enableShutdownHooks()` in `main.ts` for SIGTERM. (source: NE recipes/prisma, which now describes Prisma 7; NE fundamentals/lifecycle-events)
- [ ] Prisma 6: the old recipe used the `beforeExit` event; Prisma 7 removed it and the Nest lifecycle replaces it. Follow what the installed version supports. (source: NE recipes/prisma)
- [ ] A single client instance per process (a module exporting `PrismaService`, `@Global()` optional); never `new PrismaClient()` in a service/test helper. `$disconnect()` per query is forbidden. (source: P6/P7 databases-connections)
- [ ] Sized pool: on Prisma 6, `connection_limit` in the URL (default `num_cpus*2+1` split across instances) and `pool_timeout` (10 s); on Prisma 7 the pool belongs to the driver adapter (`pg`: `max`, `connectionTimeoutMillis`). Total = pool x replicas <= database limit. (source: P6/P7 databases-connections; the upgrade guide warns `pg` has no connection timeout by default)
- [ ] With PgBouncer: `DATABASE_URL` points to the pooler (`pgbouncer=true`) and `directUrl` (Prisma 6, in `datasource`) or `url` in `prisma.config.ts` (Prisma 7) points straight to Postgres for migrations. (source: P6/P7 databases-connections)
- [ ] The repository port is an abstract class used as a token, bound with `{ provide: AbstractRepo, useClass: PrismaRepo }`; an interface cannot be a token (erased at compile time). (source: NE fundamentals/custom-providers)

## 10. Errors

- [ ] Database errors are caught with `instanceof Prisma.PrismaClientKnownRequestError` and `code`, and translated in the repository into domain/application errors: P2002 (unique, `meta.target`), P2003 (FK), P2025 (required record not found), P2034 (conflict/deadlock, retry), P2024 (pool exhausted), P1001/P1017 (connection). (source: P6 reference/error-reference)
- [ ] No Prisma `meta`/message goes to the HTTP client or to logs with personal data; map it in the project's filter/edge layer (respecting the project's error convention).

## 11. Layers

- [ ] `@prisma/client` and `Prisma.*` are imported only in infrastructure (repositories, `PrismaService`, persistence module). Check: `grep -rEn "@prisma/client|from '.*generated" src --include=*.ts` lists only infrastructure/integration-test paths. `[community]` (Domain-Driven Hexagon, github.com/Sairyss/domain-driven-hexagon; the author's own caveat: separating the persistence model is overkill in a small app)
- [ ] Domain/application depend on ports (abstract class) and their own types; the repository maps the Prisma row to an entity/DTO. Generated types (`User`, `Prisma.UserCreateInput`) do not cross the boundary. `[community]`
- [ ] Controllers and HTTP DTOs do not expose the Prisma model directly (avoids leaking columns and coupling the contract to the schema). `[community]`

## 12. Tests

- [ ] Repositories and migrations have integration tests against a real, disposable Postgres (Docker, own port, `.env.test`), with `prisma migrate deploy` first and Jest in series (`-i`); no SQLite as a Postgres substitute. (source: P6 prisma-client/testing/integration-testing)
- [ ] Isolation: a schema or database per worker/suite (`?schema=<id>` in the URL or `CREATE DATABASE` per worker) `[community]`; the Prisma docs only cover a separate test database with cleanup.
- [ ] Cleanup between tests: `afterAll` deletes every table (dependency order, in a transaction) or `TRUNCATE ... CASCADE`; fixtures per suite. (source: P6 integration-testing)
- [ ] Service unit tests use `{ provide: Port, useValue: mock }`; never mock `PrismaService` in a repository test. For a module that imports `PrismaModule`, `overrideProvider(PrismaService)`. (source: NE fundamentals/testing; NE recipes/prisma)
- [ ] E2E with more than one Nest app in the same process does not leave `enableShutdownHooks` on in all of them (listener limit). (source: NE lifecycle-events)

## 13. Performance

- [ ] Minimal `select`/`include`: by default the client returns all scalars; use `select` or `omit` in listings and for heavy/sensitive columns. (source: P6 prisma-client/queries/select-fields)
- [ ] No N+1: no query inside `for`/`map`; use `include`, `findMany({ where: { fk: { in: ids } } })` or `relationLoadStrategy: "join"`. Confirm with query logging (`log: ['query']`). (source: P6 queries/query-optimization-performance)
- [ ] Large listings use a cursor ordered by a unique, sequential column (stable `orderBy`, `skip: 1`); large `skip` degrades. (source: P6 queries/pagination)
- [ ] Bulk writes use `createMany`/`updateMany`/`deleteMany`, not a loop. (source: P6 query-optimization-performance)

## 14. Personal data

- [ ] A sensitive personal-data column has a recorded decision: application-level encryption (an encrypted `Bytes`/`String` field), key outside the database, and the default `select` omits it. Prisma does not encrypt by itself. `[community]` `[not verified in docs]` (Prisma)
- [ ] Equality search on an encrypted field uses a blind index: a hash with a dedicated key, in its own column with `@@index`/`@unique`, with cost/truncation decided. (source: ciphersweet.paragonie.com/internals/blind-index `[community]`; the page does not explain the truncation trade-off)
- [ ] Query logging (`log: ['query']`) shows parameters: keep it off or masked in production; never log write `data` containing personal data. `[community]`

## 15. Prisma 6 limits (what the schema cannot express)

| Need | Status (docs v6/v7) | What to do |
|---|---|---|
| CHECK | Not in the schema nor Migrate; works in the database (P7 database-features) | Migration SQL (`NOT VALID` + `VALIDATE`); record the invariant and also validate in DTO/domain |
| Partial index | Prisma 6: not expressed. Prisma 7: `where` under the `partialIndexes` preview (P7 indexes) | Migration SQL; on 7, only with the preview accepted by the project |
| Expression index (`to_tsvector`, `lower(x)`) | Unsupported; does not show in `db pull` (P6 indexes) | Migration SQL; `migrate diff` will not cover it |
| `CREATE INDEX CONCURRENTLY` | Not configurable in the schema (P6 schema reference) | Manual SQL outside a transaction, decision recorded |
| Trigger / function / view | Outside the schema; views "not yet" (P7 database-features); triggers not covered on the page | Migration SQL; note that `migrate diff` ignores them |
| Unknown type | `Unsupported("...")`: disappears from the client | Query with raw SQL; record it |
| Database default unknown to the client | `dbgenerated(...)` | Record the expression; `@updatedAt` is not a database default |

For each row used: record the decision, cite the migration file where the invariant lives, and add an integration test that violates it and expects the database error. On `db pull` or baseline, a migration with manual SQL must not be overwritten: manual SQL is lost on squash.

## 16. Version notes (Prisma 6 -> 7 -> 8)

- Stable today: 7.10.0 (npm, 2026-08-25). Prisma 8 is a release candidate (`8.0.0-rc.22`, 2026-10-08), GA expected October 2026, and `npm install prisma` already installs CLI 8; Prisma 6 only gets security patches until 2026-11-19. (source: prisma.io/docs/orm/release-status; registry.npmjs.org/prisma)
- 6 -> 7: generator `provider = "prisma-client"` with required `output` (outside `node_modules`); `url`/`directUrl`/`shadowDatabaseUrl` move from `datasource` to `prisma.config.ts`; driver adapter required (`new PrismaClient({ adapter })`); `.env` is no longer loaded (`import "dotenv/config"`); `migrate dev`/`db push` no longer run `generate` or seed; `$use` removed (use `$extends`); Node >= 20.19, TS >= 5.4, ESM. (source: prisma.io/docs/orm/more/upgrade-guides/upgrading-versions/upgrading-to-prisma-7)
- `prisma.config.ts` (7): fields `schema`, `migrations.path`, `migrations.seed`, `datasource.url`, `datasource.shadowDatabaseUrl`; the CLI finds it at the root or via `--config`. `env()` throws if the variable is missing, even on `generate`. (source: P7 reference/prisma-config-reference)
- Prisma 8 (RC): `contract.prisma`, `migration plan`/`db migrate`, `db.transaction` without `timeout`/`isolationLevel`: nothing in this checklist applies; migrate only by recorded decision. (source: unversioned docs, accessed 2026-10-14)
- A project still on 6 does not adopt 7 patterns as "best practice": `directUrl` in the schema and `prisma-client-js` remain valid there.

## 17. Decisions each project must record

| Decision | Options | Where to record |
|---|---|---|
| Prisma version and upgrade policy (6/7/8) | pinned major; when to migrate | ADR + `package.json` |
| Id strategy | app `uuid()` / `dbgenerated` / `autoincrement` | modeling ADR |
| `onDelete` per relation and retention/LGPD | Cascade / Restrict / SetNull / soft-delete | table in the data ADR |
| Indexes on FKs | all / listed exceptions | modeling ADR |
| Invariants outside the schema (CHECK, partial, trigger) | where they live and who tests them | ADR + comment in the migration |
| Migration and deploy flow | `migrate deploy` only, in CI; exceptions (`CONCURRENTLY`) | runbook |
| Transaction boundary | unit of work / `$transaction` in the use case | architecture ADR |
| Pool and pooler | `connection_limit` or adapter `max`; PgBouncer yes/no | infra ADR |
| Test isolation | schema per worker / database per worker | testing guide |
| Personal data | encryption, blind index, log masking | privacy ADR |
